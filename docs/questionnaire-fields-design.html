Collateral Properties EAV Grid — already implemented
section-id: associated-records · grid-key: collateral_properties
Storage: USER_ANSWERS · row_index
How EAV grids work: Each row added by the user is identified by a row_index (1, 2, 3 …). Every cell is stored as a separate record in USER_ANSWERS (application_id, field_key, row_index, value). No dedicated table or JPA entity is needed — the schema is entirely schema-free. The trade-off is that reporting across rows requires pivoting the EAV table.

Guarantors DEDICATED Grid — new section
section-id: guarantors · grid-key: guarantors_list
New table: loan_guarantor
How DEDICATED grids work: Each grid row is a full JPA entity row in loan_guarantor linked to the application via application_id FK. The template marks each column with storage: DEDICATED (loan_guarantor.<column>) and includes a gridBackingTable hint so the application-service knows which entity to create/update/delete when the user adds or removes a row. Advantage over EAV: reporting, indexing, and FK constraints work naturally on the dedicated table. Use when each row is a first-class domain object (a guarantor, a director, a fee line).
