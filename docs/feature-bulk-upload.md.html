Phase 2 — Questionnaire fields bulk upload

Scope, revised from the original "full replace" decision after reviewing the actual seed data. Field-level attributes (labelKey, fieldType, storage, dropdownSource, required, order) and grid membership are fully replaced by file contents, per field/column key present in the file. visibilityRules/validationRules are carried forward unchanged for any fieldKey that already exists in the current draft/active template — the upload template has no columns for rules (deliberately — see below), so a literal full replace would silently delete every conditional rule in the section on any upload, including ones on fields the upload never intended to touch. A fieldKey new to the file gets empty rules, same as before. A fieldKey that existed before but is absent from the file is dropped entirely (that's still a real removal — full replace on membership, merge on rules for what's kept). This only ever touches a DRAFT (creating one from the current ACTIVE if none exists) — publish stays the separate, existing step.

  • Add org.apache.poi:poi-ooxml to questionnaire-service/build.gradle.

  • New endpoint: POST /sections/{sectionId}/bulk-upload, multipart file upload.

  • Flat row schema (one file covers one section's fields and grid columns together, via row_type):

    row_type Y FIELD or GRID_COLUMN

    grid_storage_type Y for GRID_COLUMN EAV or DEDICATED

    label_key Y e.g. field.annual_revenue
    field_type Y TEXT / NUMBER / TEXTAREA / DROPDOWN / RADIO — matches FieldType exactly, nothing invented
    storage_type Y DEDICATED or EAV
    dedicated_table Y if DEDICATED validated against AllowlistValidator.ALLOWLIST
    dedicated_column Y if DEDICATED same

  • Parser builds a SectionTemplateJson (from common): FIELD rows become fields, GRID_COLUMN rows group by grid_key into GridDefinition entries with their columns.

  • Rule-preservation merge, required: before saving, load the section's current template (the DRAFT if one exists, else the ACTIVE version) and index its existing fields/grid columns by fieldKey. For each parsed field/column from the upload, if a match exists by fieldKey, copy that existing field's visibilityRules and validationRules onto the newly parsed object before it's saved. If no match exists, leave the new object's rules empty (nothing to carry forward). This is a small lookup map built once per upload, not a structural change to the parser.

  • Do not duplicate draft-lifecycle logic — call the existing SectionTemplateService.createDraftRevision(sectionId, parsedTemplate) if no DRAFT exists, or updateDraft(sectionId, draftVersion, parsedTemplate) if one does. The bulk-upload endpoint's only new logic is parsing the file into a SectionTemplateJson — everything after that reuses what's already built.

  • Recommended addition, not in the original design: run AllowlistValidator.validate() against the parsed template at upload time too (currently only runs at publish), so a bad DEDICATED reference fails immediately with a row-level message instead of surfacing later at publish. Catch its IllegalArgumentException and return it as a 400 with the specific field/grid-column key that failed.

Important constraint — DEDICATED fields need two lists to agree, in two services

Confirmed directly from ApplicationService.java: DEDICATED reads/writes are not reflection and not dynamic SQL — they're a hand-written Map<String, BiConsumer<...>>/Map<String, Function<...>> in ApplicationService (dedicatedWriters/dedicatedReaders), one lambda per table.column, each calling a real typed setter/getter on the real JPA entity. This means two separate hardcoded lists have to agree: questionnaire-service's AllowlistValidator.ALLOWLIST (what a template may declare) and application-service's dedicatedWriters/ dedicatedReaders (what actually reads/writes). Bulk upload — same as the manual editor — can only reference a table.column pair that already exists in both. It cannot create a new dedicated column, entity field, or wiring entry; that remains a small manual Java change in application-service, independent of and prior to any bulk upload referencing it.

Hardening fix, worth doing as part of this feature, not deferred: currently, dedicatedWriters.getOrDefault(ref, (a, v) -> {}).accept(app, value) and the equivalent reader call silently no-op if ref isn't in the map — no exception, the value is just dropped. This was a narrow risk when DEDICATED fields were only ever added one at a time by hand; bulk upload makes a typo'd or drifted table.column string much more likely, and a silent data loss is a worse failure mode for a bulk operation than a loud one. Change both call sites to throw (e.g. IllegalStateException) when the map lookup misses, with the ref string in the message, so an allowlist/ wiring drift fails immediately and visibly instead of quietly dropping data.

Phase 3 — Section rename via API, not direct H2 edits

Currently there's no way to change a section's labelKey after creation — CreateSectionRequest accepts it once, but UpdateSectionRequest and DraftRevisionRequest only carry template. The only way to rename a section today is a direct H2 edit, which bypasses the draft/publish lifecycle this whole system is built around.

  • Add labelKey as an optional field on UpdateSectionRequest.
  • SectionTemplateService.updateDraft(): if the request's labelKey is non-null, set it on the draft entity before saving, alongside the existing template-JSON update.
  • Frontend: add a label-key text input to SectionEditor, editable the same way any other draft field is (goes through Save draft → Publish, same as everything else).

Acceptance: change a section's label through the admin UI, save as draft, publish — confirm the new label is reflected without touching H2 directly.
